# Sim — driving-algorithm test bench

Isaac Sim 5.1 / Isaac Lab 2.3 simulation of the car, used to check driving-algorithm logic before
moving it to the Pi and tuning it on the real car. The simulator produces the same three inputs the
car has, in the same units and sign conventions as `Pi5/`:

| input | simulated as | car counterpart |
|---|---|---|
| object boxes | per-object ground truth from the renderer, turned into YOLO-like boxes (see below) | `vision/apple_detector.py` → `(x1, y1, x2, y2, score, class)` normalised |
| IMU | BNO055/BNO08x model on the rear axle: gyro, accel, gravity-free accel, game rotation vector | not wired yet (ordered) |
| encoder | AS5600 on the **motor** shaft, sampled at ~1.5 kHz and median-filtered like `hardware/drive.py` | `Drive.rps`, `Drive.turns` |
| command | throttle −1..1 (negative = brake), steer −1 left..+1 right | dashboard link `{"t", "s"}`, `Drive.steer()` |

Nothing from the RL work (policy, rewards, PPO) is left. The vehicle dynamics are the calibrated
model from the old RL simulator (`real_car_calibration.md` in the old repo), re-expressed per unit
of motor duty.

## Layout

```
Sim/
  assets/blender/Track.blend        source of truth for the track (edit this)
  assets/blender/export_track.py    Blender -> USD + JSON export (headless)
  assets/export/                    what the sim loads: track_objects.usdc, walls.usdc, track.json
                                    (generated by scripts/export_track.sh, git-ignored)
  assets/car/mushr_nano_v2.usd      car model (re-dimensioned at load: wheels, wheelbase, mass)
  source/rc_sim/
    interface.py        car <-> algorithm contract (plain Python; valid on the Pi)
    algorithms/         driving algorithms + camera geometry (plain Python + numpy; valid on the Pi)
    config.py           EVERY tunable number, with where it came from (MEASURE = still a guess)
    detector_model.py   synthetic YOLO          imu_model.py   BNO IMU     encoder_model.py   AS5600
    track.py            track.json: objects, centre line, spawn, lap progress (sim only, not for algorithms)
    car.py, sim.py      Isaac scene, vehicle dynamics, multi-rate sensor loop
    viewer.py, run.py   live view and entry point
  tests/                unit tests for everything that does not need Isaac
  scripts/              install.sh, export_track.sh
  runs/                 one folder per run (git-ignored)
```

## Setup

```bash
cd Sim
./scripts/install.sh            # uv venv with Isaac Sim 5.1 + Isaac Lab 2.3.2 (pip wheels, no submodule)
./scripts/export_track.sh       # Track.blend -> assets/export/ (generated, not in git; needs Blender)
export OMNI_KIT_ACCEPT_EULA=YES
```
NVIDIA driver 550–580 (Isaac Sim 5.1 crashes on ≥ 590). Tested on an RTX 3070, driver 580.

## Running

```bash
uv run python source/rc_sim/run.py                          # gate_follower, Isaac window + viewer
uv run python source/rc_sim/run.py --algo manual --real-time --set episode.wall_force_thresh_n=1e9
uv run python source/rc_sim/run.py --headless --no-view --episodes 5 --laps 2   # batch
uv run python source/rc_sim/run.py --headless --no-view --record              # save viewer frames
uv run python source/rc_sim/run.py --param v_max=2.5 --set detector.fp_rate_per_frame=1.0
uv run --no-sync pytest tests/
```

* `--set section.field=value` overrides anything in `config.py`, e.g. `camera.hfov_deg=120`,
  `camera_hz=120`, `car.max_steer_deg=24`, `episode.reverse=true`, `episode.spawn_x=1.5`.
* `--param name=value` overrides an algorithm parameter (`DEFAULTS` at the top of its file).
* The car spawns at world (0, 0) — the middle of a straight — facing along the track.
* A run ends on: the requested laps, **wall contact (= failure)**, flip, driving the wrong way,
  no progress for 5 s, or the time limit.
* Every run writes `runs/<time>_<algo>/`: `config.json`, `log.jsonl` (per control step: true pose,
  speed, command, applied command, boxes delivered; `--log-sensors` adds every box / IMU / encoder
  sample), `summary.json` (laps, lap times, crashes), and with `--record` the viewer frames.
* Speed: ~0.3–0.5× real time on an RTX 3070 with the 60 Hz camera. `--real-time` only slows it down.
  `--set camera_hz=30` is roughly twice as fast when driving by hand.

Viewer: left is the detector's view (fisheye) — green = detection with score, red = false positive,
grey = object in view the detector missed, yellow = horizon. Right is a car-up map, 1 m grid:
blue/orange = left/right track objects (ringed green when detected), cyan = the algorithm's
landmarks, magenta/yellow crosses = its left/right labels, white = its centre line, yellow dot =
pursuit target, green = driven path.

## Track workflow

`assets/blender/Track.blend`: `Track` (curve + geometry nodes instancing the object along both sides
of `TrackCurve`), `MainWalls` (collision-only walls), `TrackCurve` (centre line). After editing:

```bash
./scripts/export_track.sh
```

The export evaluates the geometry nodes and splits the realized instances back into one prim per
object (`/Track/Object_000…`, ordered along the track), written with Z up / Y forward. `track.json`
holds each object's position, size, side and arc length, the centre line and corridor statistics.
Because every object is its own prim, the renderer's instance segmentation says which pixels
belong to which object, so boxes are generated in software — no YOLO needed. The object shape can be
anything; the sim reads the meshes. Walls are loaded invisible to the camera and act only as the
failure trigger. The old repo's assets (`Training/assets`) are not used.

## How the boxes are made (`detector_model.py`)

For each rendered frame (60 Hz): the renderer's instance segmentation gives each object's visible
pixels, and its mesh projected through the lens gives its full (unoccluded) box. From these:

* **size** — detection probability ramps up between 4 and 10 px on the short side (640×360 frame)
* **occlusion** — visible / expected pixels: below 25 % never, above 60 % fully; mildly occluded
  objects get their full box, heavily occluded ones only the visible part
* **frame edge** — objects mostly outside the frame are dropped, the rest clipped
* **motion blur** — yaw rate × exposure × focal length reduces detection and widens boxes
* **temporal behaviour** — misses and box jitter (centre ~3 % of size, size ~5 %) are AR(1)
  per object, so they flicker and wobble like a real detector instead of being independent noise
* **false positives** — short-lived ghost boxes in the ground band (0.3 per frame by default)
* **NMS** at IoU 0.7, so objects lined up along a straight merge
* **delivery** — ~24.5 ms latency (measured on the car), 0.5 % dropped frames

All knobs are in `DetectorCfg`.

## Camera (`CameraCfg`)

Arducam IMX708 with the 120° M12 lens, modelled as an equidistant (f-θ) lens: its 120° H × 66.7° V
over a 16:9 sensor is the f-θ signature. At 720p the car uses the 1536×864 sensor mode, which crops
the central ⅔ of the sensor → **80° × 45°** for the detector (the 2304×1296 full-FoV mode gives 120°
but only 56 fps: `--set camera.hfov_deg=120`). Isaac renders pinhole images, so the sim renders a
wider pinhole view and projects geometry through the lens model; the viewer warps the image to
match. The algorithm uses the same lens model (`algorithms/geometry.py: CameraModel`); on the car
replace it with a calibrated one.

## Writing an algorithm

```python
from rc_sim.algorithms.base import Algorithm
from rc_sim.interface import Command, SensorFrame

class MyAlgo(Algorithm):
    name = "my_algo"
    def reset(self, car):            # CarInfo: wheelbase, steer limit, camera model, encoder scale, ...
        super().reset(car)
    def step(self, f: SensorFrame) -> Command:   # called at control_hz (60)
        # f.detections: DetectionFrame(t_capture, t_available, [Detection]) delivered since last call
        # f.imu: [ImuSample], f.encoder: EncoderReading(rps, turns) - motor shaft
        return Command(throttle=0.2, steer=0.0)
```
Register it in `algorithms/__init__.py`, then `run.py --algo my_algo`. Algorithms only import
`interface` and numpy, so the file can go to the Pi as is.

`gate_follower` (the baseline) does encoder + gyro odometry, maps boxes to object positions by
size-based ranging, keeps a short landmark memory, labels objects left/right against its previous
centre line, builds gates, grows a centre line and pure-pursuits it with a curvature/braking speed
profile. Current result: it can lap (~64 s, ~1.3 m/s average) but is not reliable yet: 2 of 5
one-lap runs with different seeds completed; failures are in the hairpins and the fast right-left
S-bends. A starting point to improve on, not a finished controller.

## Still to measure on the real car (all in `config.py`, marked MEASURE)

1. Camera mount: height (0.22 m assumed), pitch (7° down assumed), x position; the real lens
   calibration.
2. `encoder.motor_turns_per_wheel_turn` (10 assumed): push the car 1 m, read `Drive.turns`.
3. `car.esc_duty_per_throttle`: the dynamics were fitted with the old motor driver; fit the
   Hobbywing ESC from encoder logs of throttle steps.
4. `car.max_steer_deg` (28° assumed): the current `steering.json` amplitude of 270 µs is ~20° by
   the old protractor table. At 20° the car's minimum radius (0.51 m) is larger than the track's
   tightest centre-line radius (0.45 m).
5. IMU mount position and axes once it is installed.
